## 5. 迭代中发现的问题

- MMU 调试最初在 `0x1000` 处捕获到的是 GDB 检查客体内存触发的调试查询，不是 CPU 取指。通过调用栈和访问类型区分后，增加 `MMU_INST_FETCH`、M 模式等条件，只记录真实 CPU 路径。
- 宿主 GDB 的 Python 断点最初只依赖断点 condition，回调仍记录了不相关事件。将目标地址与调用者检查放进 stop 回调后，观察收敛到目标访存。
- 优化版 QEMU 中部分局部变量显示为 `<optimized out>`，且 GDB 的符号显示可能不直接打印汇编标签。改为结合可见参数、调用栈、实际 PC、ELF 符号和最终数据结果验证，不把变量不可见或行号跳转误判成页表错误。
- SLUB 的测试以真实 PMM 页数恢复作为状态不变式，并在三个分配器下验证，防止仅在某一个分配器上掩盖页数取整或释放约定问题。当前记录的测试均通过，没有把未发生的 SLUB 故障写成历史问题。

### 7.先定义 Buddy 的数据结构和不变式

**我的 Prompt：**

> 请在现有 RISC-V ucore 物理内存管理框架中设计一个 Buddy System 管理器。保持 `struct pmm_manager` 接口不变，使用 `Page` 描述符管理空闲块。请说明为什么需要按 order 分组的空闲链表，以及 `PageProperty`、`property`、`page_link` 和全局 `nr_free` 分别承担什么职责。

**我的设计判断：**

> 每一阶的空闲块都要有独立的链表；只有块首页可以设置 `PageProperty`，`property` 保存块包含的页数；每阶还要记录页数，并保证所有阶页数之和等于全局空闲页数。检查函数不能只检查链表非空，还要验证块大小、地址对齐、边界和计数。

这一阶段我先确定“什么状态算正确”，再实现具体操作。这样分配和释放可以围绕同一组不变式检查。

### 8. 处理初始空闲区不一定对齐的问题

**我的 Prompt：**

> `init_memmap(base, n)` 收到的连续内存区可能起点不对齐，长度也不是二次幂。请检查直接把它当作一个 Buddy 块是否会破坏伙伴地址计算，并设计一种不会跨出空闲区边界的拆分方法。

**我的判断：**

> 不能假设整个空闲区就是一个自然对齐的大块。应当从当前地址开始，选择不超过剩余长度且满足自然对齐的最大二次幂块，反复拆分直到整个区域都被登记。这样每个块都满足块起始页号是块大小的整数倍，后续才能使用异或找到伙伴。

我在这里重点检查了三个边界：块不能越过 `base + n`；块起点必须对齐；拆分后的剩余区域不能遗漏或重叠。

### 9.实现分配、分裂和非二次幂请求

**我的 Prompt：**

> 实现 `alloc_pages(n)`，要求任意 `n > 0` 都能工作。先向上取整到二次幂，再查找足够大的空闲块；如果没有同阶块，就从更高阶块逐层分裂。请明确请求页数、实际块大小和 `nr_free` 应如何变化。

**我的实现要求：**

> 请求 3 页时实际取得 4 页块，但返回给调用者的仍是整块首页；空闲页数必须减少 4，不能减少 3。分裂产生的后半块要重新放入低一阶链表，被选中的前半块继续向下分裂。

我把“请求大小”和“实际占用大小”分开处理，避免非二次幂情况下出现越界复用或空闲页数错误。

### 10.实现释放和逐级合并

**我的 Prompt：**

> 实现 `free_pages(base, n)`。根据与分配时相同的 `n` 还原块阶，用物理页号异或计算伙伴。请只在伙伴同阶、完整、空闲且未保留时合并，并说明如何保证合并过程中链表和两个页数计数器同步。

**我的设计要求：**

> 合并时先确认伙伴是当前阶的空闲块头，再把伙伴从对应阶链表移除。移除伙伴既会减少该阶页数，也会影响全局空闲页数，两个计数必须同步更新。合并后取地址较低的块作为新块头，并继续检查更高一阶伙伴。

我还要求释放路径检查块的地址边界和阶对齐，避免错误传入的块被并入相邻内存区域。

### 11.设计可重复的测试，而不是只测一次正常分配

**我的测试 Prompt：**

> 请设计不依赖整机内存碎片顺序的 Buddy 测试。覆盖块分裂、伙伴合并、内存不足和非二次幂请求，并在测试结束后恢复分配器状态，不能影响后续内核运行。

**我的测试方案：**

> 先从真实分配器取得一个连续 32 页区域，保存原链表状态和全局空闲页数，再在这个区域上建立独立的 Buddy 状态。测试完成后恢复原状态，并把 32 页区域归还给真实分配器。

具体测试顺序如下：

1. 初始化 32 页，确认得到一个 32 页空闲块。
2. 分配两个 8 页块，确认地址相邻、按 8 页对齐，空闲页数变为 16。
3. 按顺序释放两个 8 页块，确认能够合并为 16 页，再继续合并为 32 页。
4. 请求 3 页，确认按 4 页对齐并占用 4 页，释放后能够完整合并。
5. 请求“空闲页数 + 1”，确认返回 `NULL` 且空闲页数不变。
6. 每个阶段都检查块头、`property`、地址对齐、边界和各级空闲页计数。

我采用固定 32 页测试区域，是为了让分裂和合并结果可以精确断言，而不是依赖整机内存当前碰巧形成的碎片状态。

### 12. 根据失败结果定位计数问题

**我的调试 Prompt：**

> 释放测试中块头已经显示为 32 页，但全局空闲页数却变成了 56。请从合并路径检查是否存在某个计数被重复计算或漏减，并优先通过页面计数和链表不变式定位问题。

**我的定位过程：**

> 块头大小为 32 说明结构合并本身已经发生，问题更可能在计数维护。检查发现：从伙伴所在阶链表删除块时只减少了该阶页数，没有同步减少全局 `nr_free`；合并结束时又把完整块加入全局计数，于是旧页数被重复保留。

修复时要求两个计数一起更新：

```c
free_area[order].nr_free -= current_pages;
nr_free -= current_pages;
```

这次失败说明测试不能只检查“最终块大小正确”，还必须检查两个计数器的关系。
